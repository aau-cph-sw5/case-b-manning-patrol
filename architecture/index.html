    Architecture¶

    System Context¶

    The Manning/Patrol Compliance System documents steward presence and patrol activity in the Copenhagen Metro during night operation. It consists of three deployable components that communicate through versioned contracts.

    Components¶

    Android App (Steward Client)¶

    Location: apps/android/ Stack: Expo SDK 57, React Native, TypeScript

    The steward-facing mobile app that: - Scans BLE beacons to detect presence in station areas (concourse, platforms, trains) - Manages patrol sessions (start/stop) - Posts connection/disconnection events to the backend - Receives real-time alerts via SSE

    Backend API¶

    Location: services/api/ Stack: Python 3.13, FastAPI, SQLModel, PostgreSQL

    The central service that: - Ingests positioning and patrol events (append-only event store) - Computes compliance metrics (manning %, patrol coverage) - Serves the web dashboard via SSE - Exposes versioned REST APIs defined in contracts/

    Web Dashboard¶

    Location: apps/web/ Stack: Vite, React 19, TypeScript

    The control-room dashboard that: - Shows real-time compliance status (trains manned ≥ 70%, stations patrolled hourly) - Displays historical records and overdue/at-risk stations - Consumes live updates via Server-Sent Events (SSE)

    Key Design Decisions¶

    Decision ADR Summary
    Positioning Interface ADR-0004 Areas defined by beacons; Android is source of truth for timestamps
    Database ADR-0007 PostgreSQL for relational + JSONB flexibility
    Event Store ADR-0008 Append-only event store, no update/delete paths
    Real-time Updates ADR-0011 Server-Sent Events for one-way server→client push
    Hosting ADR-0005 Ucloud (AAU) as staging environment

    Compliance Rules¶

    The system enforces two contractual requirements:

    1. Manning: Trains must be manned ≥ 70% of running time
    2. Patrol: Every station level (concourse, platform) must be patrolled at least once per rolling 60 minutes

    Coverage is computed from the append-only event store, with late-arriving reports handled per ADR-0009.

    Contracts¶

    All inter-component communication goes through versioned OpenAPI contracts in contracts/:

    contracts/api/
├── v1/                          # Initial versions
│   ├── positioning-interface/   # Observation events (simulator)
│   └── positioning-ingestion/   # Connection events from Android
└── v2/                          # Current versions
    ├── positioning-interface/   # Dashboard SSE stream
    ├── positioning-ingestion/   # Patrol session + connection events
    ├── positioning-adjustment/  # Manual adjustments (draft)
    └── health/                  # Health check endpoints

    See Contracts Guide for versioning rules.
